# 关于 Serverless RAG

## 1. 动机

iGuide 的核心能力，是围绕 UIUC 校园信息进行检索、理解与回答。

目前使用的架构已经具备“知识库检索 + 模型回答”的能力，但随着功能复杂度上升，原有架构开始暴露出明显问题：

1. 前端直接承担 AI 编排 \
   浏览器不仅负责界面交互，还在做知识检索、结果融合、prompt 拼接等工作。这会导致前端逻辑越来越重，也会让系统边界变得不清晰。
2. 模型缺少主动工具调用能力 \
   旧架构并没有任何策略分支，直接查询RAG并喂给模型。模型本身没有机会决定该查什么、查几次、何时切换信息源，因此实际上几乎没有发挥出 Agent 模式的优势。
3. 知识检索链路过于分散 \
   旧方案中，本地知识、网页搜索、用户记忆等能力并没有在统一的数据和工具层上表达，长期维护成本较高。
4. 低可扩展性 \
   一旦要新增更复杂的能力，比如精确 grep、宿舍对比、课程筛选、签证政策辅助等，就必须继续堆叠前端逻辑，架构会越来越难维护。

因此，重构的核心不是把项目从一个给予暴力 prompt-stuffing 的问答系统升级为基于服务端 Tool-Use 的校园信息 Agent 系统。

## 2. 旧架构

旧架构可以概括为：

- 浏览器接收用户提问
- 前端服务层决定是否查知识库、是否查网页
- 前端把检索结果和用户记忆一起拼进 prompt
- 最后把这个大 prompt 发给模型

对于早期敏捷开发，这种方式可以快速产出 MVP。但到了中后期，它的缺点会越来越明显：

- 逻辑分散在前端，难以统一管理和配置
- 前端很难承担更复杂的多轮工具调用
- 对安全性、可观测性、成本控制都不够友好
- 新增能力时，耦合度必然快速上升

## 3. 新架构

出了实现真正的 Agentic 能力之外，重构的另一大目标是采用完全的 serverless 的服务端。

Serverless 的核心在于*前端仅交互，服务端进行决策和路由，对应托管平台负责承载*。

新的主路径如下：

1. 第一级：浏览器 / Cloudflare Pages
2. 第二级：Cloudflare Worker
3. 第三级：各个 vendor / API 服务
   - Supabase
   - DeepSeek API
   - Tavily API
   - 托管 Embedding API

### 3.1. 前端完全去除编排逻辑

前端以后主要负责：

- 发送用户消息
- 接收 SSE 流式响应
- 展示工具调用状态
- 展示最终回答

将以下责任剥离：

- 决定是否检索知识库
- 决定是否调用网页搜索
- 手动拼装大段 prompt
- 主导整个 RAG 流程

这让前端职责更清晰，也让界面层和智能层的边界更加明确。

### 3.2. Cloudflare Worker 成为核心后端

新的 Cloudflare Worker 除了边缘网关外，还承担了核心的 Agent Runtime 角色：

- JWT 鉴权
- 路由和限流
- 启动模型推理流程
- 给模型暴露工具列表
- 接收模型的工具调用请求
- 执行工具并把结果回传给模型
- 通过 SSE 把过程和结果流式返回给前端

可以把它理解为一个轻量的服务端 Agent Runtime。

### 3.3. Supabase 成为统一的数据与检索层

新架构里，Supabase 除了存储用户记忆之外，还承担了更核心的知识检索职责：

- 文档存储
- 文档切片（chunks）
- 向量检索
- 全文检索
- 混合搜索 RPC
- 用户记忆与对话记录

### 3.4. Embedding 走托管 API，而不是默认自建 VPS

不再自行维护 VPS 而是调用第三方 embedding 模型：

- 可以显著减少自维护基础设施
- 更符合 serverless-first 的整体方向
- 让团队把精力放在产品和能力设计，而不是维护 embedding 推理服务

## 4. 数据流示例

### 4.1. 用户发起问题

用户在前端提出一个问题，例如：

- “ISR 附近有哪些 dining option？”
- “帮我比较 PAR 和 ISR 的宿舍体验。”
- “今年 UIUC housing policy 有什么更新？”

### 4.2. Worker 启动服务端 Agent Loop

Cloudflare Worker 收到请求后，会把当前对话上下文交给模型，并同时提供一组工具能力，例如：

- `search_knowledge_base`
- `web_search`
- `grep_docs`
- `custom_skills`

此时，模型不再只是被动接收资料，而是可以主动判断：

- 是否需要检索知识库
- 是否需要查网页
- 是否需要做精确匹配
- 是否需要调用更高层的技能（如宿舍对比）

### 4.3. 工具负责获取信息，模型负责组织回答

工具的职责是“找信息”，模型的职责是“组织答案”。

这意味着系统内部形成了更合理的分工：

- 检索层负责召回和筛选
- 工具层负责能力封装
- 模型层负责判断与表达

相比旧架构，这种方式更接近真正的 Agent 系统，而不只是“带检索的大 prompt”。

### 4.4. 回答过程对用户可见，但不必暴露底层细节

系统会通过 SSE 把回答流式返回给前端，同时可以展示轻量的状态提示，例如：

- 正在搜索知识库
- 正在搜索网页
- 正在使用宿舍对比技能

这样做的好处是：

- 用户感知更自然
- 过程透明度更高
- 不需要把原始工具输出直接暴露给用户

## 5. 优势

从项目管理和团队协作的角度看，这次升级的价值主要体现在四个方面。

### 5.1. 可扩展性

新架构下，新增能力的流程变得简单：

- 增加一个工具
- 增加一个技能
- 调整 Worker 的工具注册

### 5.2. 薄前端

前端不再承担智能编排职责后：

- 页面逻辑更轻
- 调试边界更清晰
- 风险更容易控制
- 新成员更容易理解前端代码职责

### 5.3. 提高控制力

把核心决策集中到服务端之后，团队将更容易做：

- 可观测性
- 成本控制
- 限流和回退策略
- 统一错误处理
- 统一 feature flag 切换

对后续稳定运营和持续迭代的优势非常明显。

### 5.4. 降低基础设施维护负担

采用 serverless-first 和托管 embedding API 之后，默认生产路径不再依赖专用 VPS。这意味着：

- 更少的机器维护工作
- 更少的故障点
- 更低的部署复杂度
- 更容易交接和扩展团队
